# The Executor: Power Struggle

A browser-based 2D fighting game built with vanilla JavaScript and HTML5 Canvas. No build step, no framework, no backend.

## Running locally

Serve the folder with any static file server, then open it in a browser:

```
python3 -m http.server 8080
```

Then visit `http://localhost:8080`.

A local server is recommended over double-clicking `index.html` directly — a couple of browsers are inconsistent about local asset loading from `file://` URLs, and this is also exactly how it'll be served once deployed.

## Project structure

```
the-executor/
├── index.html            entry point, loads css + js
├── css/
│   └── game.css
├── js/                    loaded in this order (classic scripts, shared global scope)
│   ├── fighter.js         Fighter class, sprite loading, CPU AI controller
│   ├── input.js           keyboard state + menu/gameplay input handling
│   ├── combat.js          hit resolution, round win/reset logic
│   ├── stages.js          parallax background rendering
│   ├── characterSelect.js roster data + character-select screen
│   └── game.js            fighter instantiation, HUD, menus, main loop
└── assets/
    ├── characters/
    │   ├── white-noise/<animation>/<frame>.webp
    │   ├── liberty-belle/<animation>/<frame>.webp
    │   └── botanist/<animation>/<frame>.webp   (in progress, see below)
    ├── portraits/         character-select roster tile art
    ├── logos/             stylized character name graphics
    ├── stages/             background layers -- memorial stage's files at the top level,
    │   └── bayou/          each other stage in its own subfolder (see js/stages.js)
    └── ui/                title screen, character-select backdrop
```

**Note on the JS files:** these are loaded as ordinary sequential `<script>` tags, not ES modules — they share one global scope, the same way the original single-file prototype worked. That was a deliberate choice: splitting into real ES modules would mean threading shared state (`keys`, `p1`, `p2`, the canvas context) through explicit imports/exports, which is a bigger, riskier change than "move this code to its own file." This gets the folder structure and separation of concerns without that additional risk. Converting to real modules later is a reasonable follow-up once the game has more coverage.

**Note on character sprites:** `js/fighter.js` loads and renders every character's animations through one data-driven registry (`CHAR_ANIMS`, `SPRITES`, `SIMPLE_STATE_ANIM`) instead of per-character code. Adding a character or a new animation for one that already exists is a data change — add or extend that character's entry in `CHAR_ANIMS` with `{ animName: frameCount }`, drop the frames at `assets/characters/<key>/<anim-folder>/<i>.webp` (folder names are in `ANIM_FOLDER`), and it's wired up automatically: no new loading code, no new render branch. A character can have any subset of animations — `draw()` falls back to the placeholder box for any state it doesn't have art for yet, so a roster slot can be built up incrementally across sessions. The handful of things that aren't plain per-animation data (the special move's hitbox/choreography, its dash timing, which crouch frame is the "settled" pose, a display-height correction) live in small per-character lookups near the top of `fighter.js` (`SPECIAL_BOUNDARIES`, `SPECIAL_DUR`, `CROUCH_HOLD_AT`, `CHAR_HEIGHT_SCALE`) — a character with no entry there just gets sane generic defaults.

**Note on character height:** every character renders at a fixed 180px sprite height by default, which only lines characters up visually when their art fills a similar fraction of its own 500x720 canvas. White Noise's compact hoodie-and-hood silhouette leaves more empty headroom above him than Liberty Belle's flowing hair or Botanist's leaf cloak do, so without correction he renders noticeably shorter than the other two at the same 180px. `CHAR_HEIGHT_SCALE` in `fighter.js` (currently `{ seth: 1.165 }`) corrects this per-character at render time — it's a display-only multiplier applied in `drawSpriteFrame()`, separate from the fixed `w`/`h` used for hurtbox/hitbox math, so it doesn't touch hit detection. If a new character renders at a noticeably different height than the rest of the roster, tune this rather than re-exporting their art.

**Note on stages:** `js/stages.js` supports more than one stage the same way `fighter.js` supports more than one character — a stage is picked per-match, not fixed. `STAGE_FOR_CHAR` maps a stage name to the character keys that should trigger it (checked against whichever two characters were chosen, right before `resetRound()` in `input.js`); anything not matched falls back to the default memorial stage. A stage is a back layer (drawn first, usually revealed through cutouts in what's drawn on top of it) and a front layer, each animated however that stage needs — the memorial's back layer flashes lightning at random, the bayou's cycles continuously so the water/gators read as alive. Even though the memorial's and bayou's back/front source photos happen to share the same pixel resolution (1659x948 back, 1672x941 front), each stage keeps its own independent scale/position constants (`MEMORIAL_*` vs `BAYOU_*`) rather than sharing one — see the note below on why matching pixel dimensions doesn't mean matching composition. The bayou's front-layer scale (`BAYOU_FRONT_SCALE`) is pinned near the minimum that still covers the canvas width with no gaps, which isn't alone enough to make the room read as small relative to the fighters — the remaining adjustment is `STAGE_HEIGHT_SCALE` in `fighter.js`, which upscales fighters specifically on a given stage (currently `{ bayou: 1.6 }`), applied alongside `CHAR_HEIGHT_SCALE` in `drawSpriteFrame()`. That 1.6 (and the matching `BAYOU_BAND_SCALE_K`) were derived from the room's own grand piano, whose real-world height is well known, rather than guessed by eye — see the calibration note above `BAYOU_BAND_SCALE_K` in `stages.js`. The bayou's back layer only needs to cover the window cutout it's seen through, not the full canvas, and is positioned by centering it on the *window's* span (measured directly from the front layer's transparent pixels) rather than the canvas's. The bayou additionally layers a looping band animation on top of its front layer, but that overlay is *not* drawn at the front layer's scale/position — see `BAYOU_BAND_SCALE_K` and `BAYOU_BAND_ANCHOR_SRC` and the note on matching pixel dimensions below; a background human figure needs its apparent scale checked against an actual fighter, the same as a character sprite would. The band's anchor point also isn't on the main floor the fighters stand on (`BAYOU_STAND_Y_SOURCE`) — the piano and band both sit on a small raised, curved dais, so `BAYOU_BAND_ANCHOR_SRC`'s y is that dais's own surface height, found by scanning the front layer's image for the riser's top edge rather than reusing the floor line.

## Current roster

**White Noise**, **Liberty Belle**, **The Botanist** (he/him), **Frontman** (he/him, a music-themed villain — vinyl-disc special move, sonic-blast punches), **Lady Voix** (she/her, paired with Frontman on the bayou stage — voice/sound-themed attacks: a mic-stand soundwave blast special, sonic-burst punches), and **P.H.I.** (he/him, a steampunk gladiator-android — arm-cannon punches, a special that summons a ghostly historical figure who hands him a stone tablet to smash) are playable — all six have a complete moveset (walk, idle, jump, crouch, light/heavy attacks, crouching and airborne variants, block, special move, victory/defeat animations, hitstun reaction). The Botanist's defeat animation is a themed variant where he collapses into a mound that sprouts and blooms into a flower rather than staying visible prone — that's intentional, not a bug. Botanist's, Frontman's, Lady Voix's, and P.H.I.'s specials have no hand-tuned hitbox/dash choreography of their own yet (see the note in `CHAR_ANIMS`) — they borrow White Noise's until each gets its own branch in `attackHitbox()` and `update()`. Frontman's, Lady Voix's, and P.H.I.'s `jumpForward` also reuse the same frames as `jumpNeutral`, since only one jump sheet was generated for each — that's fine, `SPRITES` doesn't care whether two animation names point at literally the same files. Lady Voix's `crouch` only uses 4 of her 8-pose source sheet's frames (standing through fully-crouched) — the sheet's second half is a mirrored ascent back to standing that the engine never plays (see `CROUCH_HOLD_AT`'s default of "hold on the last frame," which already lines up with a 4-frame trim). P.H.I.'s `crouch` needs a `CROUCH_HOLD_AT` override of its own (`1`, not the default last-frame) since his 3-frame sheet's deepest pose is the *middle* frame — the last frame is already partway back up to standing. P.H.I.'s `victory` is unusual: the user supplied 4 separate 8-frame sheets, each the same choreography but with a different ghostly historical/philosophical figure materializing in the smoke — rather than picking one and discarding the rest, all 4 were concatenated into a single 32-frame sequence (`getVictoryFrameIndex()`'s `Math.min(count-1, ...)` doesn't care how long the animation is), so a round win plays through all four figures as one longer celebration.

Four more character slots (Rainwalker, The Coyote, Archi-Tech, Echo) exist in the character-select roster with portrait art + name logos, but have no sprite sets started yet.

## Known gaps

- No sound or music.
- No single-file build/bundle step — this is meant to be served as-is.
- No grabs/throws — blocking is currently a fully safe option.
- No intro poses — round start is instant.
- Four roster slots are locked pending full movesets (see `ROSTER` in `js/characterSelect.js`).

## Asset tooling

`_tools/split_sheet.ps1` splits a multi-pose AI-generated sprite sheet (transparent PNG) into individual frames, using column-density local minima to find the true gaps between poses — robust even when trailing effects (motion lines, dust, hair) leave faint pixels bridging adjacent poses. `_tools/find_band.ps1` finds vertical content bands by row-density, for the pre-crop step described below. `_tools/server.ps1` is a minimal static file server (plus a `/save` POST endpoint) used to drive a browser-canvas compositing pass for scale calibration and final WebP export, since this machine has no Python/PIL or ImageMagick available — Chrome's canvas is the only working image encoder here. The original source sheets for every character are kept in `_tools/<character>_src/` in case frames ever need re-deriving (different crop, different scale, more frames).

Things that have bitten this pipeline in practice:

- **Labeled sheets contaminate the crop.** Some generated sheets carry a title banner at the top, a description blurb, and/or numbered circle labels under each pose. `split_sheet.ps1`'s column-based bbox spans the *full* image height, so it will happily include that banner/label text in the "tight" per-frame crop. Run `find_band.ps1` first — it computes a row-density profile and reports contiguous content bands — and pre-crop to just the band containing character content before running `split_sheet.ps1`. Sheets with no banner/labels (a plain character-only sheet) don't need this step — check for it, don't assume it.
- **A number label can sit closer to the feet than it looks.** Even after picking a content band, a label just below the feet can still land inside the crop for poses with a wide stance — the safe cutoff is often only a handful of pixels below the shortest character's feet. If a processed frame shows a stray black circle fragment at the bottom, trim the band tighter (crop a diagnostic strip around the boundary and look directly at the pixels) rather than guessing at a wider margin.
- **Multi-row sheets don't always separate cleanly.** A sheet with poses laid out in more than one row usually has clean whitespace between rows (crop each row's band separately, same as above), but trailing effects (a dust trail, a growing vine) can bridge two rows with zero fully-transparent rows between them anywhere across the width, so `find_band.ps1` reports one giant run instead of several. When that happens, crop each row by a manually-determined pixel boundary instead: crop diagnostic strips around the suspected row transition and read off where one row's content actually ends and the next begins.
- **Scale can drift between sheets for the same character, in the same session** — and drift a lot: Botanist's walk sheet needed ~1.15x, his crouch/light-punch sheets ~0.85x, and his strong-attack/jump-attack sheets ~1.8x, all calibrated against the same White Noise reference frame, all generated within the same session. Calibrate every new sheet against a reference frame independently; never assume a scale factor established for one of a character's sheets carries over to a sibling sheet.
- **A scale factor derived for one version of a sheet doesn't carry over when that sheet gets replaced, even under the same filename/purpose.** Lady Voix's original crouch sheet was calibrated at a 1.28x correction; when the user later supplied a redone crouch sheet as a straight replacement, reusing that same 1.28x (instead of re-deriving it against the *new* file's own standing-pose frame height) overshot badly — the correct factor for the new sheet turned out to be ~1.12x. The tell was comparing the new sheet's own frame-0 height (560px) against idle's (~627px) directly, rather than trusting a previously-recorded constant. Treat a replacement file exactly like a brand-new sheet for calibration purposes, even if it's filling the exact same role as the one it replaced.
- **A pose-invariant way to sanity-check a whole moveset's scale at once, once every sheet is wired in:** render each animation's frame 0 side-by-side at the character's actual in-game `drawSpriteFrame()` scale, then measure each one's *visible* (non-transparent) pixel height in that rendered output — not the source image's raw crop dimensions, which conflate pose (arms up vs. down, stride length) with true scale. Every one of Lady Voix's standing-ish animations (idle, walk, block, light/heavy punch, special, hitstun, defeat, victory) measured 131-132px tall this way once wired up, confirming they needed no per-sheet correction beyond the two (crouch, victory) whose *source* frame-0 height was directly comparable to idle's and visibly off by more than 10%.
- **A multi-hit combo sheet can bleed a limb into the wrong frame's crop.** On Botanist's crouching-attack sheets, the punch's extended fist from one pose ended up as a small disconnected blob inside the *next* pose's column segment — density-based splitting only guarantees the boundary falls in a low-density column, not that every pixel on each side actually belongs to that frame's own pose. It won't always show up in `split_sheet.ps1`'s bbox numbers (a disconnected blob at a different height than the main body can keep the column density nonzero right through where the "gap" should be, so nothing looks wrong in the log). Actually look at every processed frame before compositing; if a stray fist/prop appears floating at one edge, crop that fixed pixel range off that one frame's raw PNG before it goes through scale calibration and export.
- **Not every sheet has a transparent background.** Botanist's Hitstun sheet was exported with an opaque decorative card background (a textured dark vignette) instead of the usual transparent PNG the rest of his sheets use — `Bitmap.GetPixel` alpha samples came back non-zero even at what looked like empty space. A simple color-distance chroma key was too risky to attempt automatically here since the background's dark olive tone sits close to the character's black hair and dark clothing in RGB space — a bad key would eat into the art rather than just failing loudly. The pragmatic fix is to ask for the sheet to be re-exported with a transparent background like its siblings, rather than trying to rescue it computationally.
- **Scale can drift mid-sheet, not just between sheets — and side-by-side comparison isn't sensitive enough to catch it.** Frontman's victory sheet is split across two files, and the drift line wasn't at the part1/part2 boundary — it was at the exact frame within part1 where a background glow effect first appears. That frame, and every frame after it (including all of part2, generated once the glow motif was established), needed a *larger* scale factor (0.8) than the plain frames before it (which were correct at their existing ~0.75-0.85). This slipped through an initial side-by-side grid comparison against the White Noise reference twice in a row: first the mismatch wasn't caught at all (each part was only calibrated against its own frame 0, and both looked individually plausible), and then a follow-up "fix" based on another side-by-side grid actually moved the scale further from correct (down to 0.55) because a ~10-15% size difference is genuinely hard to judge by eye across separate panels. What actually worked: render the candidate frame directly on top of an already-correct frame (both anchored at the feet) using canvas `globalCompositeOperation = 'difference'` at ~50% alpha, sweep the scale, and pick whichever value collapses shared rigid landmarks (a mic stand, in this case) into a single sharp shape instead of a visible double-image — this is far more sensitive than eyeballing two separate panels, and it's worth using as the *default* verification method for any scale claim, not just a fallback when something looks off. A cheap first-pass audit for the more obvious cases: render several frames in a row at fixed game-scale (180px height) side by side and look for a size pop between adjacent frames, the way `verify*.html` scripts in this pipeline do — but confirm anything it flags (or anything a user reports) with the overlay technique before trusting a corrected value.
- **Matching pixel dimensions between two images doesn't mean they share an apparent scale.** The bayou stage's band photo and its room photo happen to be the exact same canvas size, which made it tempting to composite them 1:1 — but the band was shot "closer" than the room, so a musician rendered roughly twice as tall as a fighter standing on the same floor. Pixel dimensions matching is a coincidence of how the art was generated, not evidence about the scale of what's depicted; a background human figure needs the same kind of scale check as a character sprite (render it next to an actual fighter and compare), not an assumption that reusing another layer's transform will line it up. The same trap applies to reusing another *stage's* scale constants just because the source photos happen to share a resolution — the bayou originally reused the memorial's `FRONT_SCALE`/`BACK_SCALE`, and while that didn't break anything visually obvious on its own, it coupled two stages' tuning together for no reason; each stage now keeps independent constants.
- **A room's front layer can have a hard floor on how small it can be made.** Shrinking a stage's front layer to make fighters look relatively bigger only works until the layer's drawn width can no longer cover the canvas — past that point it opens a black gap at the edges during camera panning. The bayou hit this floor (`canvas.width / sourceWidth`, plus a small margin) well before the room looked "small enough" next to the fighters. Once a front layer is already at that floor, the remaining adjustment has to come from the other side: `STAGE_HEIGHT_SCALE` in `fighter.js` upscales fighters specifically on that stage instead of shrinking the room further.
- **A back layer seen through a window only needs to cover the window, not the canvas** — and its floor-scale constraint should be measured against the window's actual transparent span in the front layer, not guessed. For the bayou, that meant scanning the front layer's alpha channel for the window cutout's real pixel bounds (a PowerShell `System.Drawing` column/row scan, same technique as `find_band.ps1` uses) rather than eyeballing it, and centering the back layer on the window's midpoint rather than the canvas's — the window isn't centered on the canvas either.

- **Calibrating a brand-new character's `CHAR_HEIGHT_SCALE` needs a different technique than the difference-overlay trick above** — that trick depends on two images sharing a pose/landmark (the same character's own frames), which a new character never has against the existing roster. What works instead: render the new character's tightest-bbox frame and an existing correctly-scaled character's frame side by side, both anchored to the same floor line and drawn at their *current* game heights, then measure each one's actual visible (non-transparent) pixel extent on that render — not the raw source image dimensions, since `drawSpriteFrame` always stretches an image to the same fixed height regardless of how much of that image is empty padding versus character. Lady Voix's frames were split_sheet-cropped edge-to-edge with almost no padding, so her visible content filled 100% of her drawn box, while Frontman's reference frame's visible content only filled ~73% of his — rendering them at the "same" height without correcting for that made her look dramatically taller even though both were technically drawn at an identical pixel height. The fix is a `CHAR_HEIGHT_SCALE` entry equal to the ratio of the two measured visible extents (here, ~0.73), the same mechanism used for White Noise but in the opposite direction (shrinking an over-filled crop instead of growing an under-filled one).
- **A character with only some animations built is safe to wire into `CHAR_ANIMS` immediately** — `draw()`'s placeholder-box fallback (see the note on character sprites above) means partial roster entries never need to be hidden from the engine, only kept `unlocked: false` in `ROSTER` so players can't select them through the UI yet. Confirmed via a 40,000-tick stress test with fully randomized inputs (movement, attacks, blocks, specials) against a fighter that only had `idle` and `crouch` art — zero crashes, since every other state correctly falls through to the placeholder.
- **When several source sheets for the same animation are the same choreography with only a decorative element swapped, concatenating them costs nothing.** P.H.I.'s user-supplied victory art was 4 separate 8-frame sheets — identical robot poses each time, but a different ghostly figure materializing in the smoke — clearly meant as parallel variants, not sequential parts of one longer move. Rather than picking one and losing the other three, all 4 were exported into one `victory/` folder as a 32-frame sequence (`0-7`, `8-15`, `16-23`, `24-31`). `getVictoryFrameIndex()`'s `Math.min(count-1, Math.floor(stateTimer/7))` doesn't hardcode an expected length anywhere, so a longer animation needed zero code changes — only `CHAR_ANIMS`' frame count. Before reaching for a randomized-variant system (which nothing in this engine supports yet), check whether the simple animations-are-just-frame-counts architecture already gets you the content for free.
- **A crouch sheet's deepest pose isn't always its last frame.** P.H.I.'s 3-frame crouch sheet goes shallow → deepest → partway back up, not shallow → shallow → deepest — so `CROUCH_HOLD_AT`'s default (hold on the last frame) would have held on a pose that's already re-extending, not the fully crouched one. Caught by comparing each frame's crop height (shortest = most crouched) rather than assuming index order matches crouch depth; fixed the same way as White Noise's and Liberty's own overrides, just with a different index. Always check this per character rather than assuming the default is right.
- **Whether a scale-drift check applies to a whole sheet batch or just one sheet depends on how the art was generated, and both patterns show up in this project.** Lady Voix's sheets came in over two separate requests days apart and each needed independent per-sheet calibration (crouch and victory drifted from idle *and* from each other). P.H.I.'s 17 sheets arrived in one batch and turned out internally consistent — every standing-pose animation except victory matched idle's scale exactly with zero correction — except victory, which was uniformly ~1.65x too small across all 4 of its files (a batch-wide drift, not a per-file one, confirmed by checking each file's own frame-0 height before assuming one correction covered all 4). Don't assume either pattern going in; check each new sheet's standing-pose frame-0 height against idle's before trusting that "the rest of this batch is probably fine too."

See the hitstun frames under `assets/characters/*/hitstun/` and the Botanist frames under `assets/characters/botanist/` for worked examples of this pipeline.
